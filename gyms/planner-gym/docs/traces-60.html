Understand the four experiments and train/test windows

These are 60 experiment-specific test inputs derived from 11 source variants, not 60 independent datasets. A case ID starts with A (aggregated) or D (disaggregated), followed by HT or LC. The last component uses S for a small deployment and L for a large deployment, followed by its case number. Each experiment group has 10 small and 5 large cases. Deployment size is unrelated to the S/L suffix used in some latency-profile names.

Aggregated workers perform both prefill (processing the prompt) and decode (generating output tokens). Disaggregated deployments use separate prefill and decode workers, so the two pools can use different parallelism and allocations.

HT uses attention data parallelism 8 and MoE expert parallelism 8, with TP 1, and a 50 ms inter-token-latency (ITL) target. TTFT targets are 2 or 5 seconds, depending on the case. LC uses attention DP 1 / expert parallelism 1: aggregate and decode workers use TP 8, while disaggregated prefill workers use TP 4. Its ITL target is 15 ms and TTFT target is 0.5 or 1.5 seconds. LC is the low-concurrency/latency-focused regime, but these configs do not impose a separate low-concurrency client cap: every engine has max_num_seqs=256, and requests follow the case's scaled arrival trace. HT is not guaranteed to have a larger arrival rate than LC for every source.

All four groups currently use fixed allocations, round-robin routing, zero warmup and zero modeled KV-transfer delay. They measure the static serving baseline, not a trained planner. Results rank by goodput per GPU: throughput meeting the case's latency objectives, normalized by GPU usage. The groups change engine parallelism, latency targets and calibrated input scale, so a cross-group difference is not an isolated measurement of topology alone.

Separate unscaled training-history files are now prepared for five sources. RAGPulse, Azure Code, Azure Conversation and ART use days 1–4 as history and day 5 as test; BurstGPT uses days 1–7 as history and days 8–14 as test. Qwen and Mooncake remain held-out: their full short traces are test inputs and have no independent history in this package. The five histories can be used for training a shared policy evaluated on these held-out sources. The CSV includes each case's history path, request count, size and checksum.

History files contain workload traffic at the original 1x rate, shared by cases using that source; they are not 60 separately scaled training inputs. All 60 expanded benchmark files still contain test traffic only, and each static config uses 0 s warmup. Offline RL still needs training rollouts with states/actions/rewards and a validation interval reserved within history. Training or tuning on the test windows would make evaluation in-sample. See training-history.md for preparation commands and the training workflow.

Duration means the offered trace window, not simulation wall time. Source windows are relative to each source's origin; generated test timestamps are rebased to zero. Short traces include their final timestamp; configs extend the half-open measurement endpoint by one floating-point step when needed. Sizes are uncompressed decimal MB (1 MB = 1,000,000 bytes). CSV retains exact bytes, source-window seconds, hashes and engine settings. Scaling changes request counts within the same window; alpha < 1 thins requests, alpha > 1 replicates them, with the frozen recipe's seed and jitter. It is not a train/test ratio or an arrival-speedup setting.
